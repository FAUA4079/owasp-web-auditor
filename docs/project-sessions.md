# Project configuration and isolated account sessions

For CHK09–CHK12 and the new `--assess` / `--prompt-credentials` options, see
[authenticated-assessment.md](authenticated-assessment.md). The preflight behavior
described below remains available.

This increment adds an AuditShop account preflight. It verifies that each supplied
credential pair authenticates as the expected user ID and role. It does not test
IDOR, authentication bypass or any other vulnerability. Existing CHK01–CHK08,
automatic AI reports and public scan commands retain their existing behavior.

## Install

Run the installer in the existing auditor project root. It checks the source
version before writing, creates a backup, and refuses incompatible changes.
No additional Python dependencies are needed. Finish or retain the old source
for paused scans before upgrading: code fingerprint changes invalidate old resume
checkpoints. Completed reports can still be read.

```sh
.venv/bin/python install_project_sessions.py
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m auditor --project config/auditshop.project.json --validate-project
```

## Configuration

`config/auditshop.project.json` is a secret-free example for the fixed AuditShop
instance at `http://127.0.0.1:8088`. It expects customer A ID 101 and customer B
ID 102, both with role `customer`. It references environment variable names;
never put password or cookie values in this JSON or commit them to Git.

Schema version 1 accepts exactly: `schema_version`, `base_url`, `auth_adapter`,
`accounts`. Each account requires `alias`, `username_env`, `password_env`,
`expected_id`, `expected_role`. Configure one to four distinct IDs and aliases.
The only supported adapter is `auditshop-json-v1`; arbitrary websites, OAuth,
MFA, bearer-token authentication and browser login are not supported yet.
Base URLs must be origin-only HTTPS or literal loopback HTTP (127.0.0.1 or ::1).
HTTP localhost aliases and non-loopback HTTP are rejected for credential transport.

## Commands

| Option | Purpose |
| --- | --- |
| `--project FILE` | Load a project JSON; requires one of the two modes below |
| `--validate-project` | Validate offline; no credential reads or HTTP requests |
| `--check-accounts` | Login, verify identity, attempt logout for each account |
| `--profile FILE` | Apply the existing request, timeout and response-size limits |

The preflight is separate from `--assess`. Neither project mode accepts
`--url`, `--resume` or `--checks`. AI/output options apply to assessment reports,
not to this preflight. It writes no report, result file or checkpoint and sends nothing
to the AI provider. Normal scans still attempt automatic AI reporting.

## Run against the local lab

Keep AuditShop running in its own terminal. Use the passwords generated by that
lab database's `init-accounts` command, not your Kali login password. Account
initialization does not print existing passwords again; do not reset a lab with
data you need simply to repeat this check.

This prompt-based launcher works in Kali bash and zsh. It keeps entered passwords
out of shell history and out of command-line arguments. They are passed only to
the auditor child process via environment variables.

```sh
cd ~/owasp-web-auditor
.venv/bin/python - <<'PY'
import getpass
import os
import subprocess
import sys

env = os.environ.copy()
env['AUDITSHOP_A_EMAIL'] = 'alice@example.test'
env['AUDITSHOP_B_EMAIL'] = 'bob@example.test'
env['AUDITSHOP_A_PASSWORD'] = getpass.getpass('Customer A password: ')
env['AUDITSHOP_B_PASSWORD'] = getpass.getpass('Customer B password: ')
result = subprocess.run([
    sys.executable, '-m', 'auditor',
    '--project', 'config/auditshop.project.json', '--check-accounts',
], env=env)
raise SystemExit(result.returncode)
PY
```

If credentials are already in the named environment variables, the equivalent is:

```sh
.venv/bin/owasp-auditor --project config/auditshop.project.json --check-accounts
```

Expected successful output:

```text
customer_a: Verified
  Cleanup: logout_acknowledged
customer_b: Verified
  Cleanup: logout_acknowledged
Requests attempted: 8
Identity verification only; no vulnerability scan or AI review was performed.
Session secrets were not saved. Logout acknowledgement is not a revocation test.
```

`Verified` means `/api/me` returned the expected ID and role. It does not mean the
account or website is secure. Each account uses GET `/api/csrf`, POST `/api/login`,
GET `/api/me`, then POST `/api/logout`. The first three requests run for each
account before final cleanup. POST requests here only create/revoke sessions;
no orders, carts or business data are modified.

## Controls and limitations

- Each actor has a separate in-memory HTTP client/cookie jar. Login rotation is
  handled by that jar, and the login response supplies the new CSRF token.
- All actors and logout attempts share one request counter, deadline and ledger.
  Every attempted request, including failures, consumes budget. Cleanup cannot
  bypass an exhausted budget. Authentication redirects are never followed.
- TLS verification stays enabled; proxy environment variables are ignored.
- Credentials, headers, raw responses, identity details and tokens are never
  included in preflight output/ledger, AI input, reports or checkpoints.
- The console prints only configured aliases, closed reason codes and counts.
- Exit 0 means every identity was verified and logout returned 204. Exit 1 means
  config, verification or cleanup failed. Ctrl+C exits 130; remote sessions may
  remain until expiry if interrupted or limits prevent cleanup. Local jars are
  closed and discarded. No session-resume feature is claimed.
- Logout acknowledgement does not establish that the server invalidated the
  session. A separate revocation check is needed, especially for SHOP-14.
- `unexpected_http_status` can mean invalid credentials or a server refusal;
  `identity_mismatch` means the supplied account did not match the configured
  identity. `network_error` usually requires checking the lab server. Fix the
  cause before proceeding; no automatic login retries or password guessing occur.

Read-only ownership checks are now available through `--assess`; see the
authenticated assessment guide for prerequisites and limits.
